Production scripts — inspect the real KEK & CEK

HSM KEK (Azure Key Vault Managed HSM) — list key versions and see which is current:

# list all versions of the KEK
az keyvault key list-versions \
  --hsm-name <your-mhsm-name> \
  --name hsm-master-kek \
  --query "[].{version:name,enabled:attributes.enabled,created:attributes.created}" \
  --output table

# show current key version (non-extractable — bytes never leave the HSM)
az keyvault key show \
  --hsm-name <your-mhsm-name> \
  --name hsm-master-kek

CEK — Cache Encryption Key (regular Azure Key Vault secret) — stored in a separate vault because Managed HSM does not support the Secrets API:

# show secret metadata (no value)
az keyvault secret show \
  --vault-name <your-vault-name> \
  --name hsm-dek-cache-key \
  --query "{name:name,enabled:attributes.enabled,created:attributes.created,expires:attributes.expires}"

# provision / rotate the CEK (32 random bytes, base64-encoded)
python scripts/provision_dek_cache_key.py \
  --vault-name <your-vault-name> \
  --secret-name hsm-dek-cache-key

7. Consumer Application Table — payments-svc's own database

This service never stores ciphertext — the calling app does, in its own schema, right next to its ordinary columns. Creating an account here calls /encrypt for the account_number field only; everything else is plain non-sensitive data. A single ciphertext column stores everything needed for a future decrypt — no separate EDEK ID, IV, or tag columns required. Every account here shares the same DEK Name (customers.account_number) — create a second account and watch Latest EDEK Records stay flat instead of growing, same reuse behavior as panel 2's DEK Name field.

Envelope Encryption Architecture

How a request flows from a calling app through authentication, the encryption service, and the HSM — and where the cross-app grant check and audit log sit in that path. This is the same diagram presented at the start of the design review, kept here as a standing reference alongside the live demo.

@@ARCHITECTURE_DIAGRAM_SVG@@

Structural changes from the original design-review diagram: PlainID / PBAC is now shown as a standalone external shared policy service that both client apps and the HSM service may depend on — a dashed yellow arrow from the Core Service to PlainID shows the optional service-side PBAC check. Auditor SPN is now a separate vertical box outside the Azure subscription boundary (red dashed panel, right side) — it accesses Azure Key Vault and the EDEK Store directly across the boundary with read-only permissions, and is not part of the encryption solution itself. The Redis DEK Cache uses versioned keys ({slot}:{kv_version}:{edek_id}) — e.g. alpha:3f8a2b:{edek_id} — so reusing a named slot (alpha→beta→alpha) never causes collisions: the Azure KV secret version changes on every write, making the old slot key distinct. The CEK Rotation Service is a separate K8S service (Rotation SPN, write-only on KV secrets) that runs every 4 hours and rotates immediately on recovery. It writes new CEK bytes to the inactive slot first, then updates current_key. Pods poll every 30 s (Service SPN, read-only), call rotate(new_cek, slot, kv_version) on change, and fall back to the previous slot during the ~30 s convergence window. The Grants + Rotation box covers cross-app decrypt grants and KEK rotation under separate scopes (grant vs rotate).
